## 1. 개요

### 1.1 목적
사용자가 Discord #작업 채널에 명령을 보내면, 4개 AI(Claude/Codex/Gemini)가 
역할을 분담하여 기획→생산→검토→재검토 순으로 작업을 수행하고,
각 단계의 진행 상황을 Discord에 실시간으로 게시하여 폰에서 원격 감시/승인 가능.

### 1.2 핵심 가치
- **역할 분담**: 각 AI가 자기 역할만 담당 (중복 업무 방지)
- **크로스 체크**: 생산자(Codex)와 검토자(Gemini)가 서로 다른 AI → 객관적 검증
- **실시간 가시성**: 모든 단계가 Discord에 게시 → 폰에서 진행 상황 실시간 확인
- **승인 게이트**: 사용자가 폰에서 승인/거부/수정 가능 → 원격 제어
- **품질 보증**: 4단계(기획→생산→검토→재검토)를 거쳐 완성도 향상

### 1.3 비유
오케스트라 지휘자(ORCH 봇)가 악보를 작곡가(Claude), 연주자(Codex), 
음악 평론가(Gemini), 지휘자 최종 확인(Claude 재검토) 순으로 진행.
각 단계마다 관객(사용자)이 박수(승인) 또는 수정 요청 가능.

## 2. 아키텍처

### 2.1 역할 정의

| 역할 | AI 봇 | 담당 작업 | Discord 태그 |
|---|---|---|---|
| 지휘자 | Orchestrator | 스레드 생성, 라우팅, 승인 게이트, 최종 검증 | [ORCH] |
| 기획자 | Claude (CL-Worker) | 요구사항 분석, 설계안 작성, 위험 평가 | [PLAN] |
| 생산자 | Codex (codex-worker) | 코드 구현, 테스트 작성, 문서 업데이트 | [BUILD] |
| 검토자 | Gemini (Gm-Worker) | 코드 리뷰, 테스트 검증, 보안 점검 | [REVIEW] |
| 재검토자 | Claude (CL-Worker) | 검토 결과 확인, 최종 승인/반려 결정 | [VERIFY] |

### 2.2 워크플로우 흐름

```
[사용자] Discord #작업에 명령 (예: "재고 시스템 버그 수정")
    │
    ▼
[ORCH 봇] 스레드 생성 + 워커 자동 참여
    │  → Discord: "[DECISION] 태스크 생성 — <명령 요약>"
    │  → Discord: "[PLAN] 기획 요청 — Claude에게 설계안 작성 지시"
    │
    ▼
[Claude — 기획] 요구사항 분석 + 설계안 작성
    │  → Discord: "[PLAN] 설계안: <3줄 요약>"
    │  → Discord: "[PLAN] 위험 평가: <위험 항목>"
    │  → Discord: "[PLAN] 예상 소요: <시간>"
    │  → Discord: "[PLAN] 승인 대기 — '승인' 또는 피드백"
    │
    ▼
[사용자] 폰 Discord에서 "승인" 또는 피드백
    │  → 승인 안 하면 대기 (시간 초과 시 안전한 기본값으로 진행)
    │  → "수정 필요"라고 하면 Claude가 설계안 수정 후 재승인 대기
    │
    ▼ ▼ (승인됨)
    │
[Codex — 생산] 코드 구현
    │  → Discord: "[BUILD] 시작: <작업 항목>"
    │  → Discord: "[BUILD] 파일 수정: <파일명> (<변경 내용 요약>)"
    │  → Discord: "[BUILD] 명령 실행: <명령어> → <결과>"
    │  → Discord: "[BUILD] 테스트: <테스트 결과>"
    │  → Discord: "[BUILD] 완료 — Gemini 검토 요청"
    │
    ▼
[Gemini — 검토] 코드 리뷰 + 테스트 검증
    │  → Discord: "[REVIEW] 코드 리뷰: <평가 요약>"
    │  → Discord: "[REVIEW] 테스트 검증: <통과/실패>"
    │  → Discord: "[REVIEW] 보안 점검: <이상 유무>"
    │  → Discord: "[REVIEW] 품질 평가: <점수/10>"
    │
    ├── 평가 7/10 이상 → [Claude 재검토]로 진행
    │
    └── 평가 7/10 미만 → [Codex 생산]으로 반려 (수정 후 재검토)
       → Discord: "[REVIEW] 반려 — 수정 필요: <항목>"
       → Codex가 수정 후 Gemini 재검토 (최대 3회 반복)
    │
    ▼ (검토 통과)
    │
[Claude — 재검토] 최종 확인
    │  → Discord: "[VERIFY] Gemini 검토 결과 확인: <요약>"
    │  → Discord: "[VERIFY] 최종 판정: 승인/반려"
    │
    ├── 승인 → [ORCH 봇 최종 검증]으로 진행
    └── 반려 → [Codex 생산]으로 회귀 (수정 항목 명시)
    │
    ▼ (재검토 승인)
    │
[ORCH 봇] 최종 검증 + 완료
    │  → Discord: "[VERIFICATION] 체크리스트 실행:"
    │     ✓ 스레드 생성
    │     ✓ 기획안 승인
    │     ✓ 코드 구현
    │     ✓ 테스트 통과
    │     ✓ 검토 통과
    │     ✓ 재검토 승인
    │  → Discord: "[COMPLETE] 태스크 완료 — <최종 요약>"
    │
    ▼
[사용자] 폰에서 완료 확인
```

## 3. 상세 규격

### 3.1 Discord 메시지 포맷

모든 진행 상황 메시지는 다음 포맷을 따른다:

```
[태그] <AI 이름>: <내용>
```

태그 종류:
- [DECISION] — ORCH 봇의 라우팅/판단
- [PLAN] — Claude 기획 단계
- [BUILD] — Codex 생산 단계
- [REVIEW] — Gemini 검토 단계
- [VERIFY] — Claude 재검토 단계
- [VERIFICATION] — ORCH 봇 최종 검증
- [COMPLETE] — 작업 완료
- [ERROR] — 오류 발생
- [APPROVAL] — 승인 관련

### 3.2 승인 게이트 규칙

| 게이트 | 위치 | 승인자 | 시간 초과 시 |
|---|---|---|---|
| G1: 기획 승인 | 기획→생산 사이 | 사용자 | 10분 후 안전한 기본값으로 진행 |
| G2: 검토 반려 | 검토→생산 회귀 | 자동 (점수<7) | 즉시 반려 |
| G3: 재검토 승인 | 재검토→완료 사이 | Claude 자동 | 즉시 판정 |
| G4: 최종 승인 | 완료 전 | ORCH 봇 자동 | 즉시 진행 |

G1만 사용자 승인이 필요. 나머지는 자동 진행.
사용자가 "긴급"이라고 말하면 G1도 자동 승인 (빠른 진행).

### 3.3 반려/회귀 규칙

- Gemini 검토 점수 < 7/10 → Codex에게 수정 요청
- 최대 3회 반복. 3회 초과 시 사용자에게 알림
- Claude 재검토에서 반려 → Codex에게 수정 요청 (별도 제한 없음)

### 3.4 작업 규모별 단계 생략

| 작업 규모 | 단계 | 승인 |
|---|---|---|
| Small (버그 수정, 단순 변경) | 기획(간소) → 생산 → 검토 | G1 자동 |
| Medium (기능 추가, 리팩토링) | 기획 → 생산 → 검토 → 재검토 | G1 사용자 |
| Large (신규 기능, 아키텍처 변경) | 전체 4단계 + 사용자 승인 2회 | G1 + G3 사용자 |

작업 규모는 Claude 기획 단계에서 자동 판단.

## 4. Discord 메시지 상세 예시

### 4.1 기획 단계 (Claude)
```
[PLAN] Claude: 재고 시스템 버그 수정 설계안

요약:
- 문제: 출고 시 picked_weight가 누락되는 현상
- 원인: outbound_mixin.py의 트랜잭션 누락
- 해결: 트랜잭션 래핑 + 불변식 검증 추가

위험 평가:
- 낮음: 기존 로직 변경 최소화

예상 소요: 15분
작업 규모: Small

[PLAN] 승인 대기 — '승인' 또는 피드백
```

### 4.2 생산 단계 (Codex)
```
[BUILD] Codex: 시작 — outbound_mixin.py 트랜잭션 수정

[BUILD] 파일 수정: outbound_mixin.py
  - line 234: self.db.transaction("IMMEDIATE") 추가
  - line 256: 불변식 검증 추가 (initial = current + picked)

[BUILD] 명령 실행: pytest tests/test_outbound.py -v
  → 45/45 pass, 0 fail

[BUILD] 완료 — Gemini 검토 요청
```

### 4.3 검토 단계 (Gemini)
```
[REVIEW] Gemini: 코드 리뷰 완료

코드 리뷰:
- 트랜잭션 래핑: 정상 ✓
- 불변식 검증: 정상 ✓
- 예외 처리: try/finally 누락 → 경고

테스트 검증: 45/45 pass ✓
보안 점검: 이상 없음 ✓
품질 평가: 8/10

[REVIEW] 통과 — Claude 재검토로 진행
```

### 4.4 재검토 단계 (Claude)
```
[VERIFY] Claude: Gemini 검토 결과 확인

검토 요약:
- 품질 8/10 — 양호
- try/finally 경고 → 수용 가능 (기존 패턴과 일치)

최종 판정: 승인

[VERIFY] ORCH 봇 최종 검증으로 진행
```

### 4.5 완료 (ORCH 봇)
```
[VERIFICATION] 체크리스트:
✓ 스레드 생성
✓ 기획안 승인
✓ 코드 구현 (outbound_mixin.py)
✓ 테스트 통과 (45/45)
✓ 검토 통과 (8/10)
✓ 재검토 승인

[COMPLETE] 태스크 완료 — 출고 picked_weight 누락 버그 수정
  수정 파일: outbound_mixin.py
  테스트: 45/45 pass
  소요: 12분
```

## 6. 제약사항 및 고려사항

### 6.1 기술적 제약
- Claude Code CLI의 channels 플러그인이 메시지를 수신해야 함 (현재 정상)
- 각 워커 봇이 Discord 스레드에 메시지를 게시할 수 있어야 함 (현재 정상)
- 사용자 승인 대기 중에도 다른 작업 처리 가능 (비동기)

### 6.2 운영상 고려
- 사용자가 승인하지 않으면 작업이 멈춤 → 시간 초과 자동 진행 필수
- Discord 메시지가 너무 많으면 읽기 힘듦 → 단계별 요약만 게시
- 워커 봇이 동시에 실행되지 않음 → 순차 진행 (기획→생산→검토→재검토)

### 6.3 보안
- 승인은 APPROVER_USER_ID와 일치하는 사람만 유효
- 봇/웹훅의 승인 무시
- 실DB 수정 금지 (테스트 DB/mock 사용)
